# Security: publishing visual-check screenshots

**Purpose.** Let the owner, ChatGPT and Claude each review screenshots through git (the `visual-results` branch) without manual hand-offs and without ever giving branch code write access.
**Owner approval:** 2026-11-17 ("option B", with the requirements below). It was built as a separate PR (#26). It needs ChatGPT's independent security review and the owner's final approval before merge, and the owner-side repository settings below before it's activated.
**Revision 2 (2026-11-18)** addresses ChatGPT's security review of `fc7000f` (two P1s, four P2s, P3 hardening). **Revision 3 (2026-11-18)** addresses the re-review of `19b4cfa`: the full standard capture matrix is now required, directory entries are fully validated, and personal-data wording is corrected. See "Review corrections" below.

## Trust model
- **Screenshots and reports are untrusted review material.** The capture job (`visual.yml`) runs **branch code**: the app, its build configuration, package scripts and dependencies. The harness-identity check makes sure the screenshots were taken by the reviewed harness *configuration*; it is a **consistency check, not an attestation**. A branch can still change what the app renders or what its build does.
- What the publisher guarantees is narrower and enforceable:
  1. only reviewed default-branch code ever holds write access;
  2. only **eligible** runs are published: authorized contributors, ordinary development branches, the branch's current head;
  3. what gets published is **bounded in form**: allowlisted file names, structurally sane JPEGs at the expected widths, a strictly validated report re-serialized from known fields, and every artifact string rendered as plain text.
- **Capture workflows hold no credentials and use no private data sources.** `visual.yml` has top-level `permissions: contents: read`, no job-level overrides, no `secrets.` references, no token use, `persist-credentials: false`, and only synthetic fixtures. A unit test enforces the workflow text. These are **safeguards, not proof of pixel content**: nothing here proves that a published image contains no personal data (an authorized branch's app could render anything), which is why screenshots are treated as untrusted review material. Branch code *could* add a `secrets.` reference in its own copy of the workflow, so **the repository must not hold Actions secrets the capture job could reach** (owner check, below).

## Data flow
1. A push runs **Visual check** (`.github/workflows/visual.yml`): read-only, branch code, synthetic fixtures, frozen clock, external requests blocked. It uploads the artifact `visual-<sha>`.
2. When that run completes, **Publish visual results** (`.github/workflows/visual-publish.yml`) starts via `workflow_run`. GitHub always runs `workflow_run` workflows from the **default branch's** definition.
3. The publish job checks out **exactly the workflow's own commit**: `github.workflow_sha`, falling back to `github.sha`, which for `workflow_run` is the default-branch tip. It uses plain `git` (unauthenticated, public repository), and `publish.mjs` verifies that `HEAD` is that commit. It then runs `scripts/visual/publish/publish.mjs` with the runner's Node.
4. The script runs these checks in order:
   - **Run integrity** (else exit 1);
   - **Eligibility** (else "Not published", exit 0);
   - **Freshness** (else Not published);
   - **Harness consistency** (else Not published);
   - **Artifact integrity** (else exit 1);
   - **Existing-results integrity** (else exit 1);
   - **Stale run** (else Not published);
   - **Freshness again**;
   - then it **builds a brand-new tree** and pushes one parentless commit with `--force-with-lease`.

## Requirements and how each is met
| Requirement | Control |
|---|---|
| Privileged publishing executes only reviewed default-branch code | `workflow_run` uses the default branch's workflow file. The job checks out the workflow's **own commit** (pinned, not a moving branch tip), and the script verifies it. **No third-party actions and no `npm install`** (zero-dependency `.mjs`). Git runs with no system or global config (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`), no prompts, and argument arrays only |
| Treat artifacts as untrusted data | The zip is parsed **in memory** by our own reader (`zip.mjs`) and fully validated before anything is written. Nothing from it is executed, imported, checked out, or used as configuration. The published output is built from validated blobs plus reports regenerated by the publisher |
| Validate provenance | **Run:** this repository, not a fork, event `push`, workflow `Visual check` at `.github/workflows/visual.yml`, `completed`/`success`, id, sha and branch matching the event.<br>**Artifact:** exactly one, unexpired, named `visual-<sha>`, from that run and commit.<br>**Report:** its `branch` and `commit` must equal the run's |
| Eligibility (review P1) | Both the pusher (`actor`) and whoever ran the workflow (`triggering_actor`) must be in `AUTHORIZED_ACTORS` (`tybrathwaite1-lab`; changing it is a reviewed change to `main`). The branch must be an ordinary development branch: no reserved data branches (`visual-results`, `image-scout-results`, `gh-pages`), no `dependabot/` or `renovate/`, no odd names |
| Harness consistency (review P1: not an attestation) | Publishes only if `visual.yml`, `run.ts`, `selftest.ts` and `tests/fixtures/visual/` have the same git object ids on the branch commit as on the trusted commit. Otherwise "Not published" (the artifact stays downloadable from the run) |
| Freshness and stale runs (review P2) | The branch must still point at the run's commit, checked before download and again immediately before the push. A run with an **older run id** than the one already published for that branch is never published; a re-run attempt of the same run may republish. Each folder records the full SHA and run id (`meta.json`, `REPORT.md`, README). The push uses `--force-with-lease` against the results commit that was read |
| Validate file types, paths, sizes, counts | Strict allowlist: `<width>/<route>(-fold).jpg` for widths 320, 390, 768, 1280 and 1440; `states/<name>.jpg`; `report.json`; `REPORT.md` (ignored). Limits:<br>• ≤ 400 entries<br>• ≤ 8 MB per file<br>• ≤ 120 MB extracted<br>• ≤ 80 MB zip (also enforced while streaming the download)<br>• compression ratio ≤ 50× (JPEG) or 200× (JSON)<br>• results branch: ≤ 40 folders |
| Reject symlinks, traversal, malformed artifacts (review P2: ZIP structure) | Rejects symlinks and any non-regular Unix type; absolute paths, backslashes, `.`/`..`/empty segments, non-ASCII; duplicates.<br>**Rejects:**<br>• encryption and unknown flag bits (only deflate options, data descriptor and UTF-8 are allowed)<br>• compression other than stored/deflate<br>• multi-disk archives<br>• data after the end record<br>• a central directory that doesn't end exactly at the (zip64) end record<br>• entries that don't **tile the archive body exactly**: no prepended data, gaps or overlapping ranges<br>• zip64 locators not on disk 0 of 1<br>• zip64 records that are misplaced, extended, or disagree with non-saturated end-record fields<br>• saturated fields with no zip64 value<br>• duplicate extra fields<br>• directory entries that aren't empty: they must be stored or deflated, with size 0 and CRC 0, and a deflated entry must decode to nothing<br>**Agreement:** local headers must match the central directory on name, method, **flags**, CRC and sizes. Values may be deferred only with flag bit 3; the data descriptor (with or without signature, 4- or 8-byte) must then match. Every CRC-32 and size is verified |
| Content validation (review P2: report schema; P3: JPEG) | **JPEG:** a **structural sanity check**, not a decoder or content inspection. It requires SOI; well-formed marker segments; exactly one well-formed frame header before the scan (8-bit precision, 1–4 components, length consistent); a scan header; EOI; width equal to the folder width.<br>**`report.json`:** strict. Missing or malformed required data is an **error**, never a default:<br>• `axeAvailable` must be true<br>• every route × width has exactly one shot with the expected file names<br>• accessibility results must exist at the axe widths (390 and 1280) and are recorded as **not run** elsewhere<br>• keyboard results must exist for each keyboard width<br>• hosts are validated<br>• the screenshots and the report must match exactly (no missing files, no orphans)<br>• unknown fields are dropped and the report is re-serialized<br>**Standard capture matrix (revision 3):** only a **complete standard run** is published: all five widths, exactly the 12 app routes (`STANDARD_ROUTES`), the exact seven keyboard checks at 390 and 1280 px, and exactly the four state records. Partial or non-standard diagnostic runs are **Not published** and stay artifact-only. A carried folder that is valid but no longer standard (e.g. after the route set changes) is dropped, not carried. Tests keep these constants in step with `run.ts` and `src/hooks/useRoute.ts`, so a route change must update `STANDARD_ROUTES` in the same PR |
| Rendering (P3) | `REPORT.md` and `README.md` are regenerated. Artifact strings are rendered only as **inline code spans**: control, bidirectional and zero-width characters become spaces, and backticks and pipes become look-alikes. So no HTML, links, autolinks, emphasis or table breaks are possible. All other content is fixed template text or validated identifiers (routes, widths, file names, hex SHAs, numeric run ids) |
| Existing results trust boundary (review P1) | The results branch is **never checked out**. It's fetched by object id into a fresh repository, and its tree is listed and validated:<br>• every entry must be a regular non-executable file (`100644`); symlinks, gitlinks and executables are rejected<br>• paths must be expected (`README.md` or `<folder>/{meta.json, REPORT.md, report.json, <width>/*.jpg, states/*.jpg}`), so `.gitattributes`, `.gitmodules`, legacy layouts and anything unknown are rejected<br>• sizes and counts are bounded<br>• every folder must re-validate: strict `meta.json` that maps back to its folder, the report, every JPEG, and an exact report/screenshot match<br>Anything unexpected **fails closed** and leaves the branch untouched. The new tree is built only from validated blob ids plus regenerated files. A branch **absent** from `ls-remote` starts empty; a branch that is listed but **can't be fetched** is an error |
| Folder collisions (review P2) | Folder = readable lowercase slug + 12 hex digits of `sha256(full branch name)`, so `feature/x`, `feature-x` and `Feature/X` get distinct folders. Reserved branch names are refused. A folder can never equal `README.md`, `.git` or similar. `meta.json` must map back to its folder, and a folder recorded for another branch fails closed |
| Least privilege | Workflow-level `permissions: {}`. Job: `actions: read`, `contents: write`. **The token** is in one step's environment and is used for **authenticated API reads** (run, artifact list, artifact download request) and **the final push**. It stays in the publisher process's memory for the whole run. It's removed from `process.env` at start, never passed to child processes except the push, and never placed on a command line, in a URL or in output. Git receives it through an env-scoped `http.extraheader`. The artifact-storage redirect is fetched **without credentials** |
| No shell injection | Event values are passed only through `env:`. The script uses `execFile` with argument arrays (no shell). Folder names are `[a-z0-9._-]`; step-summary text from branch names is rendered as code spans |
| Screenshots restricted to synthetic fixtures and public app content (safeguards, not proof) | The **unchanged, reviewed harness** (harness-consistency check) supplies synthetic Pulse and weather fixtures, public `drop.json`, a frozen clock, a fresh browser profile, a blocked service worker, and blocks all other external requests. The capture job has no credentials or private data sources. These safeguards **don't prove** what the pixels show: branch app code remains untrusted (see the trust model and residual risk 1) |

## Residual risks
1. **Branch-produced imagery and diagnostics are untrusted.** An authorized branch's *app* (and build) can render arbitrary pictures and text, and influence the report's diagnostics (e.g. page-error messages, keyboard details). The publisher bounds the *form* (file types, dimensions, schema, plain-text rendering), not the *content*. Pixels aren't inspected. Reviewers should treat screenshots as claims to verify, not as attestations. Synthetic fixtures and credential isolation are safeguards; they **don't prove** that published imagery contains no personal data. Only authorized contributors' branches are eligible, and they can already commit arbitrary content.
2. **The `GITHUB_TOKEN` is repository-wide** during the publish job; GitHub can't scope it to one branch. Mitigation: only pinned, reviewed default-branch code runs with it, and the recommended `main` ruleset stops it from changing `main`.
3. **Repository secrets.** Branch code runs in the capture job, so any Actions secret readable by push-triggered workflows is reachable by anyone with push access. Keep the repository free of such secrets (or use environment secrets with protection rules).
4. **The pre-merge test boundary:** `workflow_run` only activates from the default branch, so the live workflow can't run before merge. The script is covered end to end in `npm test`; live verification follows merge (below).
5. **Trust in the runner image's `git` and `node`** (GitHub-hosted). If the repository becomes private, the unauthenticated checkout and `ls-remote` fail closed.
6. **`visual-results` is force-pushed** (with a lease) by design. Anything pushed there manually either fails validation (the publish refuses until it's removed) or is replaced.
7. **Hash-suffix collisions** (48 bits of SHA-256) aren't a practical concern. A collision would fail closed via `meta.json`'s branch check.

## Required repository settings (owner, before activation)
1. **Ruleset for `main`:** require a pull request before merging; block force pushes; restrict deletions; require the `check` status (Check (branches)). This keeps any workflow token, including this one, from changing `main` directly.
2. **Settings → Actions → General → Workflow permissions:** "Read repository contents and packages permissions" (read-only default). Leave "Allow GitHub Actions to create and approve pull requests" unchecked.
3. **Fork pull-request workflows:** keep approval required for outside contributors (the default for public repositories).
4. **Settings → Secrets and variables → Actions:** confirm there are **no repository secrets** (the capture job runs branch code). Claude can't list them; that endpoint isn't reachable from Claude's environment.
5. **Delete the legacy `visual-results` branch** (synthetic screenshots from an early #25 run, in the old layout). The publisher fails closed on unknown layouts, so it would refuse to publish until that branch is gone. Afterwards the publisher recreates it.
6. **Don't add force-push protection to `visual-results`;** the publisher relies on it. Optionally add a ruleset preventing its *deletion*.

## Post-merge verification
After #26 merges (and the settings above are in place), the next push to `main` runs Visual check, then the publisher. Verify:
- the job log shows the pinned trusted commit and "Published …";
- `visual-results/README.md` lists `main`, and its `REPORT.md` shows the full SHA and run id;
- the branch is one parentless commit;
- safe refusals leave the previous results intact:
  - a test branch that changes the harness → **Not published**;
  - a re-run of an older run → **Not published (newer results)**;
  - a deliberately tampered `visual-results` → the publish fails closed and the branch is unchanged (then restore it by deleting the branch).
